# 媒体同步可靠性与自愈改造计划

本轮实现 P1 同步可靠性与 P2 媒体验证、恢复工具，让上传失败可以追踪并重试，让缺失副本能够经过内容校验后恢复。现有对象 ID、`server:` 键和画布短链接保持稳定。

本计划基于当前分支 `feat/grok2api-protocol`、提交 `4d66863`，以及用户提供的修订需求、`ic-backfill-local-copies.py`、`ic-recover-70-missing.py`。两份独立脚本与需求文档附录内容一致。2371 个对象、70 个缺失对象已恢复等生产结果采用部署端报告，不视为开发机复验结果。

## 1. 范围与现有缺口

- 当前生成媒体同步已经执行上传后的完整回读、字节数与 SHA-256 校验；但失败只有返回错误和日志，没有持久化的重试状态。
- `PromoteGeneratedMedia` 遇到非 `local-generated` 对象直接返回；`media-cloud -mode sync` 也只扫描本地索引对象，无法补传“已登记云端但实际文件不存在”的对象。
- `cloud_synced_at` 只由部分上传路径填写。为空不能证明文件不存在，非空也不能证明文件现在仍存在。
- 当前同步对所有对象使用同一把锁，云端请求会互相等待；失败回滚还会尝试删除上传目标，需要改为保留媒体并确认目标状态。
- 应用下载接口会在云端失败后回退到本地或公开 URL，不能用该接口的 200 判定云端健康。

本轮不加入 P3 的请求时实时修改画布节点、运行时同哈希兜底链，也不处理生成日志保留或压缩。版本号不变；不执行生产修复、媒体删除、备份清理或 VACUUM。

## 2. P1：持久化同步状态与可靠重试

### 2.1 状态和时间的语义

在 `storage_objects` 扩展同步状态、尝试次数、脱敏错误、最后尝试时间、下次重试时间及执行租约；记录重试的目标 provider 和对象路径，避免重试时重新选择目标。

状态区分：未检查、待同步、同步中、等待重试、已验证、需要人工处理。自动同步关闭或账号没有可用提供方属于“未执行/受阻”，不能记录为同步成功。

- `cloud_synced_at` 表示最近一次上传并完整回读验证成功的时间，属于历史事实。
- 增加云端检查时间和检查结果，区分已验证、缺失、不可达、内容不符、尚未检查。普通巡检成功不伪造过去的上传时间。
- 旧对象初始按尚未检查处理，不根据 `provider_id` 或旧时间字段直接推断健康。通过巡检逐个建立证据。
- 状态摘要和维护报告可读；原始凭据、签名 URL 和敏感错误不进入公开对象响应。

只增加相关字段和必要查询索引，沿用现有数据库初始化方式，不重写历史媒体记录。

### 2.2 统一同步流程

1. 确认对象未删除、账号及提供方允许操作，并验证本地副本的字节数和 SHA-256。
2. 持久化待同步状态和固定目标，再领取对象租约。
3. 检查固定目标：完整内容已经匹配则直接完成；明确不存在才上传；现存内容不符则报告冲突。
4. PUT 后从该目标 provider 完整 GET，流式计算字节数和 SHA-256。
5. 验证成功后，条件更新对象索引及同步状态；对象 ID、`server:` 键和 `/api/files/<id>/content` 不变。
6. 任一步失败保留本地副本和原索引，落错误状态，不删除远端文件。上传超时属于结果不确定，先检查目标，不能直接当作不存在。

生成媒体自动同步与显式补传共用这条流程。普通服务端上传的“已验证”标记也必须建立在完整回读证据上；浏览器直传登记不能仅凭客户端声明标记已验证。

已登记云端的历史对象补传回原 provider、bucket、key，不重新分配路径。原提供方失效或配置改变时明确报告受阻，不擅自迁移到其他提供方。

### 2.3 重试、并发和进程恢复

- 启动时恢复到期租约、扫描待执行队列；随后每分钟检查到期任务，不在启动时全库下载媒体。
- 暂定首次失败后的重试间隔为 1 分钟、5 分钟、15 分钟、1 小时、6 小时，并添加少量抖动；耗尽后保留状态，支持显式重新入队。
- 网络超时、连接失败、限流和上游临时错误可重试。凭据无效、无可用 provider、哈希冲突等转人工处理，避免无效请求循环。
- 默认两个对象并行处理，同一对象通过数据库条件更新领取租约，防止重复上传；长任务续租，容器重建后的未完成任务可恢复。
- 目标路径在首次入队时固定，跨日期重试仍使用同一路径。配置变化时重新验证权限和目标，不使用旧凭据继续执行。
- 自动同步开关关闭后暂停自动任务；显式补传仍遵守已有账号与用户/全局 provider 权限。只把本轮入队的任务纳入自动重试，不自动补传全部历史对象。
- 删除对象、退出或账号权限变化后，迟到结果不得恢复已删除对象或覆盖新索引。更新时校验对象快照及租约。

## 3. P2：统一 `media-verify` 维护命令

新增 Go 命令，复用现有 WebDAV/S3 客户端、MIME 扩展名规则、媒体目录及校验函数，不依赖 Python、rclone 或生产脚本的固定目录和 provider ID。

默认 dry-run；写入必须同时提供 `-apply -writes-stopped`。只读模式使用 `OpenExistingDatabase(true)`，避免正常数据库入口的 AutoMigrate 产生写入。现有 `media-cloud` 干跑也改用同一只读入口。

### 3.1 检查与修复规则

| 本地副本 | 所属云端对象 | 处理方式 |
|---|---|---|
| 完整有效 | 完整有效 | 报告通过；apply 可更新检查状态，不重复上传 |
| 缺失 | 完整有效 | 校验后原子写入本地副本 |
| 完整有效 | 明确缺失 | 补传原云端位置，并完整回读校验 |
| 缺失 | 明确缺失 | 查找同 SHA-256、同字节数的有效兄弟副本，先恢复本地，再补传云端 |
| 任意 | 超时、401/403、5xx 或配置失效 | 报告不可达，不等同于缺失，不盲目覆盖 |
| 内容冲突或缺少校验依据 | 任意 | 报告待人工处理，不覆盖冲突文件、不删除 |

`local-generated` 对象按本地索引单独处理；显式上云复用 P1，继续遵守当前存储权限。已通过既有清理流程移除的本地副本单独标记：云端健康时默认不撤销清理决定，需要显式选择回填；云端也缺失时仍进入恢复判断。

### 3.2 恢复来源与内容证明

- 云端存在性只检查对象索引指向的 provider、bucket、key，绕开应用下载接口的本地兜底。
- 公开 URL 可以在现有 SSRF 防护下作为恢复来源，但读取成功不代表原云端对象存在。
- 兄弟对象按完整 SHA-256 与字节数查询，排除自身及已删除对象；先找有效本地副本，再按兄弟对象自身配置尝试云端副本。
- 跨账号兄弟恢复仅由具有数据库维护权限的离线命令执行，始终验证完整内容，不改变目标归属、访问规则或画布引用，不向普通用户暴露其他账号信息。
- 现有本地文件也进行完整校验，不能仅凭文件存在跳过。缺少 SHA-256 或可靠大小的旧对象报告无法验证，不将当前读取结果直接认定为原始内容。
- 流式计算哈希并限制读取量；限定并发，避免视频、音频或大文件被全部加载到内存。
- 回填使用同目录临时文件，完整校验后执行文件同步、原子落盘和目录同步；不得覆盖冲突文件。磁盘不足或校验失败时仅清理本次临时文件。
- 回填成功后更新相关副本状态；不调用会重新生成 ID 或把云端对象改回本地 provider 的保存路径。

### 3.3 命令参数和报告

提供对象、账号、provider 筛选，以及 `-limit`、`-after` 游标和受限的 `-workers`。默认处理一个有限批次，报告下一游标，可中断后继续；重复运行不产生第二份对象。

每条 JSON 报告包含：对象 ID、账号 ID、provider、对象 key、本地与云端状态、预期及实测字节数、完整 SHA-256、恢复来源、兄弟对象 ID、计划/实际动作、耗时和失败原因。汇总给出检查数、缺失类别、计划修复数、实际修复数、失败/跳过数和下一游标。

dry-run 可以读取媒体以验证内容，但不创建目录、媒体临时文件或数据库状态；计划动作与实际修复必须分开显示。单对象失败不影响后续对象，有失败时使用非零退出码。

## 4. 两份运维脚本的复用边界

保留脚本已证明可用的“读取副本 → 校验 → 原子落盘”与“同哈希兄弟恢复 → 补回原路径”思路。正式代码补齐以下差异：

- 两份脚本关闭了 TLS 证书校验；新代码沿用现有受控客户端，不照搬此设置或放宽 SSRF。
- 脚本只读取全局私有配置，并尝试其他 WebDAV；新代码按对象 owner 和明确授权的 provider 解析，不把其他存储配置当作默认镜像。
- 恢复脚本只用前 64 字节的 Range 请求确认云读，正式实现要求完整字节数及 SHA-256 校验。
- 回填脚本允许缺少 SHA-256、已存在文件直接跳过；正式实现区分无法验证与完整有效。
- 脚本不更新数据库状态、没有持久化租约；正式实现补齐状态、去重和重启恢复。
- 脚本执行默认可能写入；新命令默认只读，写入门槛明确，并排除已删除对象。

## 6. 验收与部署安排

### 开发与测试证据

补充有实际失败注入的回归测试：

- PUT 失败后状态、错误和重试时间可读；随后成功，目标 ID/key 不变。
- PUT 已成功但客户端超时，下一次通过回读完成，不重复创建或删除对象。
- 云端回读内容错误时不标记已验证；本地媒体、原索引及远端文件保留。
- 同一对象并发领取仅一个成功；租约失效后可接管；被删除或被改动的对象拒绝迟到回写。
- 本地缺失、云端缺失、双缺三类分别恢复；兄弟哈希/大小不符、已删除、不可读时拒绝借用。
- 401/403、超时与 404 分开处理；完整云读校验不能被本地兜底掩盖。
- dry-run 前后数据库、目录及媒体文件均无变化；apply 拒绝缺少停写确认。
- 图片、视频、音频，以及有意清理本地副本和缺少 SHA-256 的旧对象分别覆盖。

本地实施按当前约定做静态审查与 `git diff --check`，不执行构建或语法检查。Go 回归和实际 `go build ./...`、生产镜像构建由部署/CI 环境执行并记录证据，不能只检查健康端点。

### 部署端流程

1. 先备份数据库，部署新代码并确认状态字段已建立；不凭发布触发全库写入修复。
2. 测试环境造三类副本缺失及上传失败，验证 dry-run 与 apply、错误分类和重试。
3. 对生产少量对象 dry-run，核对逐对象报告；再分页巡检全库。既有恢复完成的对象应主要报告通过，不能按历史 70 条清单重复补传。
4. 如发现需要写入修复的对象，确定维护窗口、备份并停止应用写入，再执行 `-apply -writes-stopped`；恢复应用后复跑巡检。
5. 浏览器实际验证画布显示、刷新、图片编辑和视频/音频播放；直接读取修复后的所属云端对象及稳定短链接，并核对字节与哈希。
6. 每周 cron 先只运行 dry-run 并保存报告。`-writes-stopped` 是停写声明，不会自动停止应用，不能直接放进常驻生产定时修复任务。

完整巡检需要读取媒体全量字节，会占用网络与磁盘读吞吐；按批次、低并发和维护时段执行。保留原云主存、本地兜底、保留期及独立备份确认机制，不增加新的自动清理。
